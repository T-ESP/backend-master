# Frontend Developer Integration Guide

This guide covers every API endpoint you need to build the frontend. The API runs on `http://localhost:8090` and all responses follow the same JSON structure.

---

## Architecture Overview

### How the Backend Works

The backend has **two services** that share a PostgreSQL database:

1. **Rust API** (`localhost:8090`) - Your main API. Handles CRUD operations, KPIs, and **reads** AI results from the database.
2. **AI Service** (`localhost:8001`) - Python ML service. Runs 7 machine learning models that **write** predictions, scores, and alerts into the database.

```
Frontend  --->  Rust API (:8090)  <--->  PostgreSQL  <---  AI Service (:8001)
                (reads everything)       (shared DB)       (writes predictions)
```

### Should I Call the Rust API or the AI Service Directly?

**Always use the Rust API (port 8090).** The Rust API reads all AI data from the database and returns it with proper pagination, filtering, product names, and consistent JSON format.

The AI service (port 8001) is only for:
- `GET /ai/health` - Check if the AI service is running
- `GET /ai/status` - See last run metrics (timing, success/failure counts)
- `POST /ai/run` - Manually trigger all AI models (admin use only)

AI models run automatically:
- On startup (when Docker starts)
- On a daily cron schedule (default: 2:00 AM)

You do **not** need to call the AI service before reading predictions. The data is already in the database.

### Database Tables (AI)

| Table | Written By | What It Contains |
|-------|-----------|-----------------|
| `demand_forecasts` | Demand Forecaster (Prophet) | 30-day demand predictions, stockout dates, reorder quantities |
| `product_classifications` | ABC-XYZ Classifier | Revenue class (A/B/C) + demand variability class (X/Y/Z) per product |
| `product_clusters` | K-Means Clusterer | Product groupings (Cash Cows, Rising Stars, etc.) with 6 feature scores |
| `supplier_scores` | Supplier Scorer | Delivery, quality, lead time, fulfillment scores per supplier |
| `price_suggestions` | Price Suggester (Random Forest/GBR) | Recommended prices with confidence scores and reasons |
| `price_anomalies` | Price Anomaly Detector (Isolation Forest) | Products with unusual pricing flagged as anomalies |
| `sales_anomalies` | Sales Anomaly Detector (Isolation Forest) | Products with unusual sales volumes flagged as anomalies |
| `notifications` | All models | Alerts and suggestions generated by every model |

### How Alerts Work

Alerts (stored in the `notifications` table) are **automatically generated** by the AI models whenever they detect something actionable:

- **Demand Forecaster** creates CRITICAL/HIGH alerts for products about to run out of stock
- **Supplier Scorer** creates HIGH/CRITICAL alerts for poorly performing suppliers
- **Price Anomaly Detector** creates HIGH alerts for unusual price changes
- **Sales Anomaly Detector** creates MEDIUM/HIGH alerts for unusual sales volumes
- **ABC-XYZ Classifier** creates MEDIUM alerts when a product's classification changes
- **Price Suggester** creates MEDIUM/HIGH suggestions for price adjustments (confidence >= 0.7)

Alert lifecycle: `new` -> `acknowledged` -> `in_progress` -> `resolved` or `dismissed`

The frontend should:
1. Show unread alerts count (badge) using `GET /alerts/summary`
2. Display alerts list with filtering by severity/status/model using `GET /alerts`
3. Let users acknowledge/resolve alerts using `PUT /alerts/{id}/status`
4. Optionally bulk-update alerts using `PUT /alerts/bulk-status`

## Response Format

Every endpoint returns one of these two shapes:

```json
// Success
{
  "success": true,
  "data": <any>,
  "message": "Human-readable message"
}

// Error
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "What went wrong"
  }
}
```

**Error codes you'll encounter:**
`VALIDATION_ERROR`, `DATABASE_ERROR`, `NOT_FOUND`, `ALREADY_EXISTS`, `UNAUTHORIZED`, `FORBIDDEN`, `INTERNAL_SERVER_ERROR`, `INVALID_INPUT`, `MISSING_FIELD`

## Authentication

All endpoints (except `/auth/login` and `/auth/register`) require a JWT token.

**Required header on every request:**
```
Authorization: Bearer <your-jwt-token>
Content-Type: application/json
```

The token expires after 24 hours. If you get a `401 UNAUTHORIZED` response, re-authenticate.

### Login
```
POST /auth/login
Content-Type: application/json

{ "email": "admin@example.com", "password": "adminpass" }
```

Response:
```json
{
  "success": true,
  "data": { "token": "eyJ0eXAi..." },
  "message": "Login successful"
}
```

Store the token (localStorage or memory) and send it on every subsequent request:
```
Authorization: Bearer eyJ0eXAi...
```

### Register
```
POST /auth/register
Content-Type: application/json

{
  "email": "user@example.com",
  "password": "securepass",
  "firstname": "John",
  "lastname": "Doe"
}
```

## Alerts (Notification Management)

Alerts are **automatically generated** by AI models. The frontend manages their lifecycle (acknowledge, resolve, dismiss). Think of this as an inbox for AI-detected issues.

### List Alerts (with filters)

```
GET /alerts?status=new&severity=critical&model_type=price_anomaly&limit=20&offset=0
```

| Param | Type | Default | Options / Description |
|-------|------|---------|----------------------|
| `status` | string | *(all)* | `new`, `acknowledged`, `in_progress`, `resolved`, `dismissed` |
| `severity` | string | *(all)* | `critical`, `high`, `medium`, `low` |
| `model_type` | string | *(all)* | `demand_forecast`, `classification`, `price_anomaly`, `sales_anomaly`, `supplier_scoring`, `price_suggestion` |
| `product_id` | int | *(all)* | Filter alerts for a specific product |
| `category` | string | *(all)* | `alert` (problem detected) or `suggestion` (recommendation) |
| `from_date` | date | *(none)* | Start date filter (YYYY-MM-DD) |
| `to_date` | date | *(none)* | End date filter, inclusive (YYYY-MM-DD) |
| `limit` | int | 50 | Page size |
| `offset` | int | 0 | Skip N results |

All filters are optional and combine with AND logic. Results are sorted by severity (CRITICAL first), then by date (newest first).

Response data shape:
```json
[{
  "id": 21,
  "product_id": 42,
  "product_name": "Cable USB-C 2m",
  "model_type": "price_anomaly",
  "category": "alert",
  "notification_type": "price_anomaly_detected",
  "severity": "HIGH",
  "message": "Price anomaly detected: current 16.28, expected 15.02 (score: -0.45)",
  "action_recommended": "Investigate unusual price change immediately",
  "related_result_id": 5,
  "status": "new",
  "created_at": "2026-02-05T15:00:05Z",
  "updated_at": "2026-02-05T15:00:05Z"
}]
```

**Field notes:**
- `model_type` tells you which AI model generated this alert
- `category`: `alert` = problem detected, `suggestion` = price/restock recommendation
- `related_result_id` links to the source record (e.g., the price_anomaly row that triggered this)
- `action_recommended` gives a human-readable next step

## AI Predictions (Read-Only)

All AI endpoints are **read-only**. The data is generated by the ai-service background jobs and stored in the database. You just read it through the Rust API.

> **Important:** These endpoints read pre-computed results from the database. They do NOT trigger AI model execution. Data refreshes automatically (daily cron + on startup).

### Demand Forecasts

30-day demand predictions per product. Uses Facebook Prophet time-series forecasting.

```
GET /ai/forecasts?limit=50&offset=0
GET /ai/forecasts/{product_id}
```

| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `limit` | int | 50 | Max results per page |
| `offset` | int | 0 | Skip N results (pagination) |

Response (each item):
```json
{
  "id": 1,
  "product_id": 42,
  "product_name": "Cable USB-C 2m",
  "forecast_date": "2026-02-05T15:00:53Z",
  "forecast_days": 30,
  "total_predicted_demand": "150.50",
  "avg_daily_demand": "5.02",
  "current_stock": 21,
  "recommended_stock": 180,
  "reorder_quantity": 159,
  "days_until_stockout": 4,
  "urgency": "URGENT",
  "mape": "12.50",
  "rmse": "3.20",
  "created_at": "2026-02-05T15:00:53Z"
}
```

**Urgency levels:** `URGENT` (<=7 days), `HIGH` (<=14), `MEDIUM` (<=30), `LOW` (>30)

**Accuracy metrics:**
- `mape` (Mean Absolute % Error) - Lower = better. Under 20% is good.
- `rmse` (Root Mean Squared Error) - Absolute error in units. Lower = better.

### ABC-XYZ Classifications

Classifies each product by revenue importance (A/B/C) and demand predictability (X/Y/Z).

```
GET /ai/classifications?limit=50&offset=0
GET /ai/classifications/{product_id}
```

| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `limit` | int | 50 | Max results |
| `offset` | int | 0 | Pagination offset |

Response (each item):
```json
{
  "id": 35,
  "product_id": 8,
  "product_name": "Batterie externe 10000mAh",
  "abc_class": "A",
  "xyz_class": "X",
  "combined_class": "AX",
  "total_revenue": "25439.56",
  "revenue_contribution_pct": "4.02",
  "total_units_sold": 827,
  "coefficient_of_variation": "0.323",
  "strategy": "Just-In-Time with Safety Stock",
  "priority": "CRITICAL",
  "created_at": "2026-02-05T15:00:10Z"
}
```

**ABC classes:** `A` = top 80% revenue, `B` = next 15%, `C` = bottom 5%
**XYZ classes:** `X` = stable demand (CV<0.5), `Y` = moderate (0.5-1.0), `Z` = erratic (>=1.0)

**Combined classes and strategies:**
| Class | Meaning | Strategy |
|-------|---------|----------|
| AX | High value, predictable | Just-In-Time with safety stock |
| AY | High value, variable | Regular review with moderate safety stock |
| AZ | High value, unpredictable | Large safety stock, frequent monitoring |
| BX | Medium value, predictable | Periodic ordering |
| BY | Medium value, variable | Regular review cycles |
| BZ | Medium value, unpredictable | Increase safety stock |
| CX | Low value, predictable | Automated ordering |
| CY | Low value, variable | Simple min-max system |
| CZ | Low value, unpredictable | Minimal stock, order on demand |

## AI Service (Direct - Admin Only)

These hit the Python AI service directly on port **8001** (not the Rust API on 8090). No auth required. Use these for admin/debug purposes only.

```
GET  http://localhost:8001/ai/health   # DB connection + service status
GET  http://localhost:8001/ai/status   # Last run metrics (timing, counts, errors)
POST http://localhost:8001/ai/run      # Manually trigger all 7 AI models
```

**`/ai/health`** - Returns `{"status": "healthy", "database": "connected"}`

**`/ai/status`** - Returns detailed metrics from the last model run:
```json
{
  "status": "completed",
  "total_duration_seconds": 85.19,
  "handlers": {
    "PriceAnomalyHandler": { "status": "success", "duration": 1.5 },
    "SalesAnomalyHandler": { "status": "success", "duration": 1.6 },
    "ClassificationHandler": { "status": "success", "duration": 8.0 },
    "ClusteringHandler": { "status": "success", "duration": 6.0 },
    "SupplierScoringHandler": { "status": "success", "duration": 0.2 },
    "DemandForecastHandler": { "status": "success", "duration": 28.0 },
    "PriceSuggestionHandler": { "status": "success", "duration": 41.0 }
  }
}
```

**`/ai/run`** (POST) - Triggers all models to re-run. Returns immediately with `{"status": "started"}`. Models run in background (~90 seconds total). Check `/ai/status` to see when complete.

**When to use:** Only if you need to force a refresh of AI data (e.g., after bulk data import). Normal operation is automatic (daily cron at 2 AM + on Docker startup).
